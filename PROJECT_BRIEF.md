## 2. Product Vision

Agencies managing creators juggle three kinds of knowledge that live in different places: **platform rules** (Instagram, TikTok, YouTube policies that change often), **contracts** (brand deals, talent agreements with exclusivity, usage rights, payment terms) and **performance data** (posts, campaigns, metrics). Mistakes are expensive: a violated branded-content rule, a missed exclusivity clause, a misread KPI.

**CreatorOps Copilot** is an assistant where an account manager can ask, in natural language:
- "Can we post this caption for a paid partnership on Instagram without the disclosure label?" (policy RAG + compliance check)
- "Does this brand contract restrict working with competitors, and for how long?" (clause search)
- "Which creator had the best engagement rate on Reels last month, and is that format allowed for the campaign's sponsor category?" (SQL + policy = hybrid)
- "Schedule this post for Friday 18:00 for creator X" (action tool, with human approval)

Everything is answered with **citations** (policy section + snapshot date, contract clause + page, SQL query + rows), and risky actions require **explicit user approval**.

### Why it stands out
Hybrid reasoning over documents + SQL + actions, versioned policy documents, human-in-the-loop agent design, real benchmarking of **tool-use trajectories** (not just RAG), and a fine-tuning experiment on a concrete task. It is a real-world product idea, not a generic "chat with PDFs".

### Hard constraints
- **No real client data.** All creator/analytics data is synthetic. Contracts are public datasets or synthetic.
- Keep content brand-safe and professional. Creators are generic personas (e.g. "Creator A, fashion, 120k followers").

## 4. Architecture

```
 Documents ─► Ingestion (parse/OCR → clean → structure-aware chunk → metadata → embed → upsert/version)
                        │
                        ▼
        Qdrant/Chroma (vectors + metadata) + BM25 + SQLite (analytics, schedule)
                        │
 User ► Web UI ► FastAPI ► LangGraph agent ──────────────────────────────┐
                   1. classify intent / route (policy | contract | sql | action | hybrid)
                   2. retrieval (hybrid dense+BM25, metadata filters: platform, version, doc_type) + rerank
                   3. tools (see below), run in a loop when needed
                   4. human-in-the-loop interrupt before any write action
                   5. grounded answer + citation verification + abstention if evidence is weak
                                                                          │
                          MCP server exposes the same tools ◄─────────────┘ (demo client)
```

### Tech defaults (record any change in `docs/decisions.md`)
- Python 3.11, `uv`/pip + `pyproject.toml`, `ruff`, `pytest`, type hints, pre-commit, GitHub Actions (lint + tests + tiny smoke eval).
- Parsing: PyMuPDF/`pdfplumber`, HTML to text for web snapshots (`trafilatura`), OCR fallback if needed.
- Chunking: structure-aware (headings, numbered sections, contract clauses); store `section_path`, `page`, `char_start/end`.
- Embeddings: `BAAI/bge-m3` or `bge-base-en-v1.5`; compare in an ablation. Reranker: `bge-reranker-v2-m3`.
- Vector store: Qdrant (docker) or Chroma, must support upserts and metadata filters.
- LLM: behind a single `LLMClient` interface. One hosted option (Anthropic API) and one local option (Ollama). Config by env vars.
- Orchestration: **LangGraph** (stateful graph, conditional routing, interrupts for approval, checkpointer), LangChain for retrievers/tools/prompts.
- API: FastAPI. UI: Streamlit or Gradio (a chat panel, a "sources" panel with highlighted passages, a SQL panel showing the query and rows, an approvals queue, a calendar view). A polished UI matters for the demo.
- Experiment tracking: MLflow or W&B.

### Metadata per chunk
`chunk_id, doc_id, doc_type, platform, title, section_path, page, doc_date, snapshot_date, version, is_latest, source_url, synthetic, content_hash, ingested_at, clause_type (contracts, nullable)`

Updates: re-ingesting a changed page/file (different `content_hash`) creates a new version, marks the old one `is_latest=false` and keeps history. Queries default to the latest version unless the user asks otherwise.

## 5. MCP Server and Tools

Implement as plain Python functions with typed schemas, used by the LangGraph agent AND exposed through the official MCP Python SDK.

| Tool | Type | Description |
|---|---|---|
| `search_policies(query, platform?, as_of?, top_k)` | read | policy/regulation retrieval with citations |
| `compare_policy_versions(platform, topic)` | read | diff between two snapshots of a policy, summarized |
| `find_clause(contract_id?, clause_type, query?)` | read | find clauses (exclusivity, term, termination, IP/usage rights, payment, non-compete) |
| `classify_clause(text)` | read | clause-type classifier (the fine-tuned model) |
| `run_sql(query)` | read | **read-only** SQL with validation (SELECT only, allowlist of tables, row limit, timeout) |
| `explain_schema()` | read | tables/columns description |
| `check_post_compliance(caption, platform, is_paid, ...)` | read | retrieves rules and returns a checklist verdict with citations |
| `schedule_post(creator_id, platform, datetime, caption)` | **write** | adds a row to `schedule`, **requires human approval** |

Provide `examples/mcp_client_demo.py` (and a config snippet for a desktop MCP client) to show it live.

## 6. Fine-tuning Experiment (required, one main experiment)

**Task:** contract clause-type classification for the agency-relevant clause types (e.g. Exclusivity, Non-Compete, Term/Renewal, Termination, IP/License Grant, Payment, Governing Law, Other).

1. Build the dataset from the CUAD annotations (map its 41 labels to ~8–10 agency-relevant classes + "other"), split **by contract** to avoid leakage.
2. Baselines: (a) zero-shot/few-shot LLM prompt, (b) un-tuned small encoder with a linear head.
3. Fine-tune a **small model** (e.g. DeBERTa-v3-base, ModernBERT-base or a small LM with LoRA).
4. Report macro-F1, per-class precision/recall, confusion matrix, latency and cost compared to the LLM baseline. Integrate the winner as the `classify_clause` tool.
5. Log in MLflow/W&B, write `reports/finetuning.md` with honest limitations.

Hardware: the owner's PC has an **AMD GPU (no CUDA)**, so run training on **Google Colab/Kaggle**. Keep a CPU-friendly small-subset mode for local tests.

(Optional second small experiment if time remains: fine-tune a query router instead of using an LLM router.)

## 7. Evaluation / Benchmarking (core of the grade)

Build `eval/` with versioned datasets and reproducible scripts (`make eval`).

**Dataset: at least 120 questions**, labeled by type:
- ~30 policy questions (incl. version/date-specific), ~25 contract questions, ~25 analytics (SQL) questions, ~25 hybrid questions, ~15 action/tool-use scenarios, plus ~10 **unanswerable / out-of-scope** (must abstain or refuse).
- Each item: `question, type, gold_doc_ids, gold_passages, gold_sql_or_result (if SQL), expected_tools, reference_answer`.

**Metrics**
- Retrieval: Recall@1/5/10, MRR, nDCG@10, by question type.
- Generation: faithfulness/groundedness (LLM-judge with fixed rubric + manual spot-check on a sample), answer correctness, **citation accuracy**, abstention precision/recall.
- SQL: **execution accuracy** (result equals gold result) and safety (rejected unsafe queries, test with injection-style prompts).
- Agent: routing accuracy, **tool-call accuracy and trajectory correctness**, rate of approval-required actions correctly interrupted, latency, token cost.
- Compliance check: accuracy on ~60 labeled captions (compliant vs non-compliant with reason).

**Ablations:** dense vs BM25 vs hybrid; with/without reranker; structure-aware vs fixed chunking; with/without routing (single retriever for everything); fine-tuned classifier vs LLM baseline; latest-only vs version-aware retrieval.

Include an **error analysis** with concrete failures and a limitations section.

## 11. Working Rules for Claude Code

1. Plan before coding in each phase, then implement in small steps, running tests as you go.
2. **Never invent results.** Every number in docs/reports must come from a real run with a saved log or artifact. If something was not run, say so.
3. **Never fabricate sources.** Only real public documents with recorded URLs and licenses. Synthetic data must always be labeled synthetic.

5. The SQL tool must be read-only and validated. Write actions always require human approval.
6. Simple, readable, typed, documented code. Tests for chunking, versioning, SQL guardrails, citation verification, MCP tools and the approval flow.
7. Reproducible: pinned dependencies, seeds, config files, `make` targets.
8. Update README and `docs/` in the same commits as the features they describe. Log trade-offs in `docs/decisions.md`.
9. At the end of each phase give a short status: what works, what is next, what is blocked, what you need from the owner.
